# Merchant collection acceptance (2.17.0 candidate)

## Wire contract

The Android collection client uses only the configured HTTPS origin and existing CookieManager session. Every request sets the exact `Origin`, disables redirects/cache, bounds request/response sizes and HTTP timeouts, and never fetches the card issuer URL. It does not use scanner tokens or anonymous check-in.

- `GET /plugins/bitcoin-rewards/{storeId}/pos/api/capability` must return `{ "available": true, "currency": "CAD", "version": 1 }` before amount entry is enabled.
- `POST .../invoices` sends UUID `operationId`, integer `amountMinor` (CAD cents), and optional exact `expectedCheckInId` captured from a successful QR/Boltcard check-in on the same configured origin/store. The entire immutable operation is committed before create. Legacy success bodies without an ID remain check-in compatible and cannot reuse a previous customer's ID.
- `GET .../invoices/{operationId}` is the recovery/status authority.
- `POST .../invoices/{operationId}/tap` sends only the strict parser-approved `boltcardUrl`; even a lost/error callback is followed by GET, never a second card dispatch.
- `POST .../invoices/{operationId}/cancel` is followed by GET even when the cancellation request errors or settlement races it.
- The explicit **Reconcile with server** button requires an operator reason (1–500 characters). The scoped transport overload sends authenticated `POST .../invoices/{operationId}/reconcile` with `reason`, the immutable persisted `amountMinor`, and optional exact persisted `expectedCheckInId`, using the original origin/store, then GET even after a lost/error ACK. The Activity must call `reconcileAndRead(operations, reason)`, not the legacy UUID-only overload, including after restart and history recovery. Refresh/poll remain GET-only. Neither action resets local identity or infers cancellation, expiry or payment from its ACK.
- The paired backend's optional reconcile identity fields must match a known operation when supplied. For an unknown/not-admitted UUID, the server uses the supplied original amount/check-in identity to durably fence that UUID before acknowledging terminal `cancelled`, so a delayed original create cannot later admit an invoice. GET must then return the same operation/amount with a validated terminal result; a 404 carrying `noOperation` remains unknown and locked, not evidence of cancellation. Android never synthesizes this fence or terminal state.
- Responses echo operation/currency/amount and a stable invoice ID. `review` can have null invoice/QR/expiry after ambiguous creation. Cancelled/expired responses can omit QR. The client never uses a callback ACK as settlement.

These capability and nullable-field details were checked read-only against the paired backend controller/service under `bitcoinrewards-lnurl-safe`; no backend files were modified by the Android task.

## Safety/UX

The authenticated trusted display exposes Collect payment on waiting or checked-in states, never a reward claim. The exact server check-in ID, not the legacy constant device ID, identifies the customer eligible for server-owned transfer. A validated bound-invoice or terminal response releases only the matching captured ID; the exact bounded server stale-check-in rejection (HTTP 400 in the paired backend) releases that capture with explicit operator guidance, while the immutable uncertain operation remains locked for server reconciliation. Other rejection/auth/network failures never release a capture by inference. No cancel-all-check-ins call is made. Staff enters the final Square-calculated total, confirms without a PIN, and hands over the device. The invoice screen has no amount editor. Camera check-in and rewards NFC are paused/guarded before launch. Payment mode consumes NFC even while busy/review/terminal but only a fresh pending, unattempted, current-lifecycle tap can dispatch.

Only non-secret operation UUID, origin, store, amount, optional expected check-in ID, invoice identity and a tap-dispatched bit are persisted. Persisting the UUID must succeed before create; persisting the tap bit must succeed before tap. Process restart reads the same operation, never creates another invoice or replays a card. Pending, review, unknown/missing operations and authentication/network failures block replacement charges. An unknown operation that never reached the server requires operator-confirmed abandonment through scoped Reconcile rather than an unsafe client reset. Only a validated terminal GET after the server's durable UUID fence permits the normal Finish flow. Operator-confirmed abandonment cancels only the exact captured check-in if it is still pending and eligible; when no captured ID exists it cancels none, and it never cancels an unrelated or changed check-in. Terminal results remain locked until explicit staff Finish; Finish atomically archives non-secret identity/status/tap metadata rather than deleting the reference. **Payment history / late settlement** reopens the same reference for authenticated GET/reconcile and keeps replacement locked if it is uncertain again. History labels are snapshots, not current settlement assertions. Return reloads/re-authorizes the trusted check-in display.

The paired server must enforce both BTCPay invoice and Square reward exclusion, transfer only the expected eligible check-in, serialize cancel/tap races, and authoritatively resolve paid/review. Cancelled/expired are trusted only as server responses after the backend established that the Lightning node is no longer payable; Android has no local expiry timer or invented terminal result. Android copy alone is not proof of exclusion.

## Automated / remaining acceptance

Added transfer/recovery coverage includes exact GUID scope isolation, legacy capture invalidation, oversized/duplicate/deeply nested success bodies, reason-bearing reconciliation, exact stale-check-in rejection, immutable expected identity, terminal history and subsequent late-status recovery. The preference model applies failed commits to process memory before reporting failure, matching Android semantics; failed archive/release synchronously restore active guards rather than treating false as rollback. The unknown-recovery transport test explicitly exercises GET 404 `noOperation` → scoped reconcile with the original amount/exact check-in → independently validated terminal GET; contradictory or still-missing GET never adopts the POST ACK. These are JVM transport fixtures, not a live backend demonstration. Durable fencing and delayed original create rejection must be verified in paired backend tests. Source wiring tests preserve the existing camera/check-in/login flows and establish separate payment API routing.
